# Edufy Academy: Settings Security

## Data separation

| Data | Stored in | Who can read | Who can write |
|---|---|---|---|
| Public settings (names, contacts, social, logos, banners text, SEO IDs, app config, maintenance) | `site_settings` (`is_public = true`) | Everyone, via `GET /api/settings/public` or `get_public_settings()` | Express server only (service role), after validation |
| Private settings (email templates and sender) | `site_settings` (`is_public = false`) | Admins (via the server) | Express server only |
| Razorpay key secret, webhook secret, email API key, Emovur token | `secure_credentials.secret_ciphertext`, AES-256-GCM encrypted | **Nobody** through the API. RLS is on with no policies; only the server's service role reads it and decrypts in memory | Express server only, super admin (Razorpay) or section admin (email/WhatsApp) |
| Encryption key | `SETTINGS_ENCRYPTION_KEY` in the **server environment** | Server process only | You (hosting panel) |
| Audit log | `settings_audit_log` | Admins (RLS `is_admin()`) | Server + banner trigger |
| Media files | Storage bucket `site-assets` (public read) | Everyone (they are website images) | Server only (service role) |

The website and app never receive a secret.
- **Public endpoint:** strips private sections and contains only validated non-secret fields.
- **Admin endpoint:** returns masked hints only, for example `••••••••a1b2`.
- **Database:** direct writes to `site_settings` from the browser are refused by the database (verified in tests).

## Controls
- **Validation on the server** for every field:
  - https-only URLs
  - phone, email, version, date, GA ID and Search Console token formats
  - lengths
  - unknown fields are dropped
- **HTML email templates** are sanitised: scripts, iframes, event handlers and `javascript:` links are removed.
- **Credential lifecycle:** save → *pending* → server-side test → *activate*.
  - A saved key is never used for real traffic until it passes the test.
  - Live Razorpay keys need the admin's password on save, activation and revert. The password is checked with Supabase Auth; the temporary session is discarded.
- **Key rotation safety:** the previous Razorpay secret is accepted for 24 h, so payments started before a key change still verify. Enrollment still happens **only after server-side signature verification** (or a verified webhook).
- **Uploads:**
  - The real file type is detected from the bytes; file names and MIME types are not trusted.
  - Size and dimension limits apply per type.
  - SVG with scripts, event handlers, foreignObject, entities or external references is rejected.
  - Storage paths are generated by the server.
- **Permissions** are checked on the server for every request. The UI hiding a section is not the protection.
- **Audit log:**
  - Records section, action, field-level old → new values (truncated), actor, time and success/failure.
  - Secrets are recorded only as `secretsChanged: ["keySecret"]`, never as values (verified in tests).
- **Rate limits:**
  - 60 settings requests per minute per admin
  - 5 password checks per minute
  - 6 gateway tests per minute
  - 5 test emails per minute
- **Maintenance mode** never blocks `/admin`, `/login` or the auth pages, and admins bypass it. The app's announcement always offers *Continue*.

## Operational advice
- Generate `SETTINGS_ENCRYPTION_KEY` once (`openssl rand -base64 32`), store it in a password manager, and set it on every server copy. Losing or changing it makes saved credentials unreadable; the server then falls back to environment keys and logs a warning.
- Give day-to-day staff restricted admin roles; keep two super admins.
- Review **Audit Log** after any payment-related change.
- If a key may have leaked:
  1. Rotate it in the Razorpay, Resend/Brevo or Emovur dashboard.
  2. Save the new key here, test it and activate it.
